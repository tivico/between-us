# 更認識你：自願試答與理解回饋執行稿

更新日期：2026-10-08。執行稿版本 `0.1.0`，對應 [候選內容 0.3.0](getting-to-know-you.md)。目前尚未核定內容或接入網站。此檔是流程與空白模板，不保存任何私人選項、人物或事件。

## 這輪要做什麼

先確認題目能否自然選答、選項是否重疊／遺漏、分享說明是否清楚，再決定哪些修訂值得做。使用者認為目前題目已夠白話，保持原題；題庫中的 12 項編輯提案不直接套用。

試答者不用替題目找問題，也不用逐題寫長篇解釋。先玩四題，指出不順的地方即可；有疑點才補問理解。一般可讀性回饋、詳細理解探問及測量驗證是不同層次，不把試玩稱成正式研究或量表驗證。

方法背景：[CDC／NCHS Cognitive Interviewing](https://www.cdc.gov/nchs/ccqder/question-evaluation/cognitive-interviewing.html)。其方法檢查理解、回想、判斷與選答。本稿借用這些觀察方向；題組、人數、順序與核對條件是本站操作提案，沒有照搬其研究樣本安排，也未獲 CDC 審核。

## 自願與資料處理

可用這段話邀請，但本稿不代為傳訊或招募：

> 我們在整理一份雙人問答，想先知道好不好回答。你可以選自己想試的四題，跳過、不分享或隨時停下都可以，不必解釋原因。沒有標準答案、不計分，也不要求你透露私人故事。選項可以自己保留，只回饋哪裡好懂或不好選。願意嗎？

目前是文件試答，不會建立雲端回合，也不承諾已存在尚未實作的保密功能。各自的選答由本人保管；若自願交換，只分享各自願意透露的部分。內容作者不收手機密碼、身份資料、私人事件、對方答案或返回憑證。

這份 repository 是公開的。完整答案及可識別的訪談紀錄不能放在 docs、src、log、測試或 commit。必要的私有工作筆記只放 Git 忽略的 `.local/qa-content-feedback/`，建立前用 `git check-ignore .local/qa-content-feedback/session.md` 確認；若未被忽略，先不要建立紀錄。本機筆記不是雲端保存或跨裝置歷史。

只記與內容修改有關、無法識別個人的摘要，例如「某題兩個選項可同時成立」；需要引用完整回饋時先確認本人願意公開。記錄保留與刪除方式另與提供回饋的人說清楚，不自動保留原始聊天或私人選項。正式網站的保存／刪除規則不能由本稿取代。

## 執行順序

1. 固定候選版本與題組。先選日常 01–04，或關心 09–12；每輪一組四題，願意再選第二組。私密題組不自動加入。
2. 確認本人自願。先說明所有特殊狀態，尤其「暫不分享」與「尚未想清楚」不同。
3. 讓本人自己閱讀和選答，先不介紹來源、標準解釋或結果建議，避免引導。
4. 只問一次整體感受：「哪一題最不好選，或有沒有想補充的地方？」沒有問題也如實記錄，不強迫找錯。
5. 若本人願意，針對疑點用下面的開放式探問。不要先說出你希望對方理解的答案，也不要追問私事。
6. 選兩則候選結果樣稿，先標明是假設組合，沒有代填伴侶答案；請本人確認描述是否超出題目、個別建議方向是否正確、是否有被要求讓步的感覺。
7. 記錄可公開的內容問題與待確認項目，分清原話、摘要、編輯推論。沒有作答時間就寫未測，不猜完成分鐘數。
8. 需要修訂時列「舊文 → 提案 → 原因 → 是否採用」，再自願重試受影響題目。未受影響題目不為了湊版本重寫。

## 有疑點才使用的探問

| 觀察方向 | 可問的句子 | 避免的問法 |
| --- | --- | --- |
| 理解 | 你覺得這題在問什麼？哪個詞不自然？ | 這題就是問期待，不是實際行為，對吧？ |
| 回想 | 這段時間容易回想嗎？沒有事件時知道可以選什麼嗎？ | 要求說出具體私人事件或人物 |
| 判斷 | 想法是否隨情境不同？資訊夠不夠回答？ | 因為你壓力很大所以應該選某項吧？ |
| 選答 | 有沒有兩項都符合、缺的做法或需要略過？ | 為什麼不選比較體貼的選項？ |
| 分享 | 不想分享時知道怎麼處理嗎？這份說明讓你以為哪些內容會被看見？ | 不分享是不是不信任對方？ |
| 結果 | 這段整理有沒有說出題目根本沒問的事？ | 你同意這則建議一定能改善關係嗎？ |

「已夠白話」可以作為可讀性回饋，但不能推定四選項都涵蓋、雙方理解一致、全部 32 題無問題或效果已驗證。不需要為取得改述而一直追問同一位試答者。

## 核定與接入條件

內容核定表目前全部待使用者核對，不自動勾選：

- [ ] 題幹／選項：32 題哪些保留、採用哪些修訂提案，無未處理的重大理解問題。
- [ ] 分享說明：暫不分享、特殊答案及解鎖後可見範圍能理解；不以前端隱藏當保密。
- [ ] 結果範圍：只作共同點、差異與探索性建議，不推測題目未詢問的行為或人格。
- [ ] 建議規則：完成要發布的規則清單；目前只有四則樣稿，不能說全部 32 題規則已完成。
- [ ] 自願回饋：記錄實際取得與未取得的內容，以及是否選擇按明示限制先行開放。
- [ ] 版本核定：明確列內容版本、結果規則版本與開放題組，保留舊稿。

核定是產品內容決定，不是研究驗證標章。核定後才能依已選範圍接入，再驗證 Node／D1 分享與完整性規則、特殊狀態、A／B 角色互換、回合快照、手機畫面與鍵盤操作，執行 `npm run check`、`npm run build`。本次是文件及來源查核，不做虛構的工程試答來補足人類回饋。

## 維護與除錯

題目不好選：先查原題與版本，再看是時窗、重疊或情境不足，僅修改相關題目。只有「已夠白話」時先保留，不據此刪除全部疑點。

建議方向反了：查規則 ID 的你／對方映射，尤其需求題不等於本人實際做法；先停用錯誤規則，不改私人答案。分享說明令人誤會時先修說明、重試理解，再接後端，不用縮小字體解決。

修改範例：02 題試答者若說「備案與排完整行程都符合」，先記這是實際回饋，再提出統一成行程細度的改法，請使用者決定是否採用；採用後更新候選題目版本及結果條件，重新試答 02 題，不改全部題目。
